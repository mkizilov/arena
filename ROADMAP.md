# Arena roadmap and handoff

This is a prioritized engineering plan, not a claim that the application is production-ready. Priorities first address incomplete original acceptance criteria and correctness/security risks, then operational and user-facing improvements.

No hardware integration is part of this repository's current scope. No attached hardware was accessed or tested; any later hardware work requires a separate authorized manual checklist.

**Estimate assumptions:** 306–522 engineering hours total, the sum of the 17 ranges below, for one engineer familiar with Elixir/OTP, Phoenix and distributed systems. Ranges include implementation, targeted tests and documentation but exclude calendar waiting for toolchains, infrastructure procurement, security audits, OS or network policy changes, and production operations. They assume project-local pinned tools, permitted loopback ports, no more than two ordinary workers, and an explicitly authorized environment for Docker-only checks. Findings may invalidate estimates; they are not measured durations.

## 1. Establish a reproducible local build and test baseline

- **Status:** Partially implemented; pinned versions exist, but no Elixir/OTP installation or dependency lockfiles were available here.
- **Scope:** Provision the pinned tools and PostgreSQL locally, resolve and commit appropriate root and load-test lockfiles, then compile and run the existing suites without disabling tests. Reconcile the manual Phoenix foundation with the original generator requirement.
- **Rationale:** Every server-side acceptance claim depends on a runnable, reproducible baseline.
- **Dependencies:** Project-local network/package access and a disposable local database; preserve the supplied sandbox.
- **Acceptance criteria:** `mix check` passes with required distribution prerequisites; load-test `mix test --max-cases 2` passes; fresh locked builds work without global installs; generator provenance is accurately resolved or explicitly accepted.
- **Effort:** 16–28 hours.

## 2. Close guest and transport security gaps

- **Status:** Partially implemented; signed guest tokens and local-only observability guards exist, but private room codes are not authentication and rate limiting is absent.
- **Scope:** Add authorization and abuse limits for guest issuance, socket joins, input, matchmaking and room-code guesses; protect tokens in transit/logging and define revocation/session policy. Replace public local-only defaults for any nonlocal deployment.
- **Rationale:** A valid bearer token or guessed room ID currently provides insufficient protection against impersonation and abuse.
- **Dependencies:** Step 1; deployment threat model.
- **Acceptance criteria:** Automated tests cover unauthorized joins, token expiry/revocation, rate limits, origin/proxy handling and secret redaction; production configuration has no reusable development credentials.
- **Effort:** 20–36 hours.

## 3. Prove and harden distributed ownership and failover

- **Status:** Partially implemented, unverified: Horde placement, discovery and replica checkpoints exist; no three-node run has passed here.
- **Scope:** Exercise local Gossip and Compose DNS, node loss, membership convergence, checkpoint ordering, startup markers, replica loss and clock translation. Resolve the LocalCluster fixed-port conflict without escaping the allowed interfaces/ports. Define a fencing or quorum approach for partitions.
- **Rationale:** Eventual consistency and a single volatile replica do not prevent competing owners or guarantee recovery under partitions.
- **Dependencies:** Step 1; project-scoped distributed VM and permitted test networking.
- **Acceptance criteria:** Three-node tests demonstrate cross-node lookup, placement and same-state recovery after abrupt node loss; partition/replica-loss behavior is explicit and tested; the original LocalCluster-start requirement is met or formally reconciled without unsafe ports.
- **Effort:** 32–56 hours.

## 4. Execute and strengthen crash/reconnect chaos tests

- **Status:** Implemented test scenarios, unverified; the required 50 consecutive chaos games were not run.
- **Scope:** Run the seeded 50-game test repeatedly; cover crashes at checkpoint/broadcast boundaries, duplicate sessions, reconnect before/after expiry and disconnected movement.
- **Rationale:** A restart or stale session can lose input, resume the wrong state or forfeit a player incorrectly.
- **Dependencies:** Steps 1 and 3.
- **Acceptance criteria:** At least 50 consecutive games pass with reproducible seeds, no leaked processes or checkpoints, and verified 10-second reconnect behavior; failures and timing are recorded honestly.
- **Effort:** 16–24 hours.

## 5. Make result delivery durable and idempotent

- **Status:** Partially implemented; transactional idempotency and retries exist, but the outbox is volatile ETS.
- **Scope:** Introduce a durable result outbox with bounded retries, recovery after VM/store loss, backpressure and operational visibility; preserve tie and duplicate-result semantics.
- **Rationale:** Pending results can be lost after a match exits or its node/store fails.
- **Dependencies:** Steps 1 and 3; database migration policy.
- **Acceptance criteria:** Failure-injection tests prove eventual delivery across process and node restarts, no double-counted stats, bounded backlog behavior and nonblocking ticks.
- **Effort:** 24–40 hours.

## 6. Validate authoritative game and power-up rules

- **Status:** Implemented in source with ExUnit/StreamData tests, unverified by Elixir execution.
- **Scope:** Run and extend deterministic properties for movement, simultaneous collisions, free-cell spawning, scoring, duration, power-ups and seeded replay; resolve any compilation or rule regressions found.
- **Rationale:** The server's pure transition core is the source of truth for every client and result.
- **Dependencies:** Step 1.
- **Acceptance criteria:** Property and unit tests pass with reproducible seeds, cover full-board and simultaneous-death edge cases, and verify score/growth invariants without weakening assertions.
- **Effort:** 16–28 hours.

## 7. Add unambiguous snapshot and delta ordering

- **Status:** Partially implemented; delta gaps trigger resync and equal-tick full snapshots are reapplied, but there is no separate snapshot revision or match epoch.
- **Scope:** Add monotonic revision/epoch identifiers to snapshots, deltas and resync replies; handle replay, stale equal-tick snapshots, recovery and protocol compatibility.
- **Rationale:** Equal-tick authoritative updates can correct state, but currently cannot be ordered against stale equal-tick responses.
- **Dependencies:** Steps 3 and 6.
- **Acceptance criteria:** Property and client tests reproduce full state through drops/reordering, reject stale revisions, and recover correctly across reconnect, power-up migration and node failover.
- **Effort:** 12–20 hours.

## 8. Verify database persistence and live leaderboard

- **Status:** Implemented migrations, writer and LiveView; Ecto sandbox tests and actual PostgreSQL behavior are unverified.
- **Scope:** Run migrations and sandbox tests, verify tie handling, idempotency, ordering, concurrent updates, retries and leaderboard PubSub refresh with real PostgreSQL.
- **Rationale:** The existing slow/failing-database tests have not demonstrated that persistence leaves ticks responsive.
- **Dependencies:** Steps 1 and 5.
- **Acceptance criteria:** Sandbox tests pass with slow and failed writes, tick responsiveness is measured, duplicate outcomes do not double-count, and leaderboard rankings refresh correctly.
- **Effort:** 16–28 hours.

## 9. Validate production release, probes and deployment

- **Status:** Partially implemented; release configuration, health checks, multi-stage Dockerfile, Compose, nginx and a failover script exist but were not run.
- **Scope:** Build and boot the locked release, run migrations, validate `/healthz` and `/readyz`, and exercise two-node DNS discovery, nginx WebSocket traffic and the failover script in an explicitly authorized Docker environment.
- **Rationale:** YAML parsing and mocked script tests do not prove that images, health checks or real failover work.
- **Dependencies:** Steps 1, 3, 4 and 8; authorized Docker access outside this sandbox.
- **Acceptance criteria:** Reproducible release/image builds and real HTTP/WebSocket probes pass; killing one node mid-match preserves the game and reconnects a real client; cleanup preserves pre-existing data.
- **Effort:** 20–36 hours.

## 10. Verify telemetry, dashboard and Prometheus export

- **Status:** Implemented event definitions, custom dashboard and PromEx integration; Elixir tests and exporter startup are unverified.
- **Scope:** Run telemetry tests, verify per-event measurements, overrun logging, scrape output, fanout estimates and local-only access across nodes.
- **Rationale:** Metrics are useful only if their units, counts and access controls are demonstrated.
- **Dependencies:** Steps 1 and 9.
- **Acceptance criteria:** Tests and live scrapes confirm tick p50/p99 histogram semantics, overrun counts, population and message metrics, and no match/player IDs appear as unbounded Prometheus labels.
- **Effort:** 10–18 hours.

## 11. Complete measured load testing and bottleneck work

- **Status:** Partially implemented; Slipstream tooling and a synthetic size fixture exist, but no required production load run or profile was performed.
- **Scope:** Run 100, 1,000 and 5,000 bots, profile with bounded `:eprof`/observer tooling, fix the demonstrated dominant bottleneck, and rerun identical scenarios.
- **Rationale:** The original load-test acceptance criteria require measured before/after behavior, not synthetic frame sizes.
- **Dependencies:** Steps 3, 6, 9 and 10; permitted project-local capacity and disposable data.
- **Acceptance criteria:** `LOADTEST.md` contains actual p50/p99, overruns, CPU, memory per match, message rates, failure counts, profile evidence and comparable post-fix results; generated datasets are cleaned safely.
- **Effort:** 32–52 hours.

## 12. Demonstrate and package hot upgrades

- **Status:** Versioned state migration and a procedure exist; no live release upgrade, appup or relup has been verified.
- **Scope:** Execute the documented isolated upgrade during a running match, validate state and power-up behavior, then design and test appup/relup ordering and rollback or a documented restart strategy.
- **Rationale:** Direct `code_change/3` tests alone do not establish safe live release or multi-node rollout behavior.
- **Dependencies:** Steps 1, 3, 6 and 9.
- **Acceptance criteria:** Real before/after tick and rule evidence is recorded, no process is force-purged, old checkpoints migrate, and the supported upgrade/downgrade boundary is tested.
- **Effort:** 24–40 hours.

## 13. Exercise real browser and channel journeys

- **Status:** JavaScript unit tests pass; real LiveView, WebSocket, canvas and browser integration are unverified.
- **Scope:** Add browser tests for guest bootstrap, quick play, private rooms, keyboard input, power-ups, results and reconnect through the proxy.
- **Rationale:** Mocked DOM and socket behavior cannot prove production browser interoperability.
- **Dependencies:** Steps 2, 6, 7 and 9; project-local browser binaries if permitted.
- **Acceptance criteria:** Two independent browser clients complete a match and reconnect after a node failure; tests bind loopback only, clean resources and pass without external services beyond the approved test stack.
- **Effort:** 16–28 hours.

## 14. Make matchmaking coherent across nodes

- **Status:** Partially implemented; match processes are distributed, but each node's quick-play queue is local and volatile.
- **Scope:** Design cluster-wide or deliberately sharded matchmaking, queue recovery, fairness and disconnect ownership; retain the eight-player/10-second rules.
- **Rationale:** Players connected to different nodes may wait in separate queues despite enough players globally.
- **Dependencies:** Steps 3 and 7.
- **Acceptance criteria:** Multi-node tests show cross-node grouping, no duplicate assignments, correct cancellation/disconnect handling and documented behavior under node loss and partitions.
- **Effort:** 16–24 hours.

## 15. Reconcile readiness, routing and degraded availability

- **Status:** Partially implemented; readiness checks membership, while nginx uses passive upstream handling.
- **Scope:** Define when a one-node survivor should receive traffic, make health-aware routing and reconnection policy consistent, and test failure/recovery transitions.
- **Rationale:** A recovered match can run while `/readyz` reports 503, and the current proxy does not route based on readiness.
- **Dependencies:** Steps 3, 9 and 10.
- **Acceptance criteria:** Documented policy is exercised under one-node loss, replica unavailability and recovery, without exposing observability endpoints or claiming quorum guarantees that do not exist.
- **Effort:** 12–20 hours.

## 16. Add reliable CI and supply-chain checks

- **Status:** Partially implemented; commands and pinned top-level versions exist, but no lockfiles or verified CI pipeline are present.
- **Scope:** Automate the complete local verification matrix with locked dependencies, safe cluster prerequisites, secret scanning and bounded workers; preserve local-only/Docker boundary distinctions.
- **Rationale:** Unrun checks and floating transitive dependencies allow regressions and non-reproducible builds.
- **Dependencies:** Steps 1, 2, 6 and 9.
- **Acceptance criteria:** CI reports rather than skips required suites, runs with no committed secrets/caches, tests release generation and documents any genuinely external-only checks.
- **Effort:** 12–24 hours.

## 17. Improve accessibility and player-facing clarity

- **Status:** Basic canvas, controls, status, score and result UI exist; accessibility and usability have not been validated in a browser.
- **Scope:** Add accessible game/status alternatives, clear reconnect/queue feedback, responsive layout and comprehensible player labels without changing authoritative rules.
- **Rationale:** A playable canvas needs usable feedback for keyboard, assistive-technology and small-screen users.
- **Dependencies:** Step 13.
- **Acceptance criteria:** Keyboard and screen-reader journeys are manually and automatically checked, mobile layout remains usable, and score, result and reconnect states are understandable.
- **Effort:** 12–20 hours.
